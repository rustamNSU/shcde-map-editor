Script Extender — прежде всего runtime SDK: он обращается к памяти и вызывает
функции запущенной игры. Это не готовая автономная библиотека чтения `.map`.
Мы используем исследованные числовые флаги, размеры и смещения как данные для
собственного парсера. SDK и его hooks не копировались и не запускались.

## Уже применено и проверено

Добавлен `semantics.py`: преобразование координат, чтение записей построек,
анализ флагов местности, диагностический экспорт кандидатов на записи юнитов и
растительности, схематическая отрисовка. Все эти операции только читают карту.

### 1. Координаты и 320 800 клеток

`src/SHCDESE.BepInEx/Interop/GameTileManagerView.cs:20` задаёт
`NativePackedTileCapacity = 320800`. Массивы действительно упакованы в ромб,
а не в полный квадрат из 640 000 клеток.

`src/SHCDESE.BepInEx/API/GameTileManagerAPI.cs:507` вычисляет индекс через
`x + MapRowLookupTable[3*y]`; обратное преобразование — около строки 535.
Наша независимая формула строит строки длиной `2, 4, ..., 800, 800, ..., 4, 2`.
Для строки y: длина `2*min(y+1,800-y)`, левый x `(800-длина)/2`, индекс —
сумма длин предыдущих строк плюс смещение от левого x.

Проверка независимыми данными: сохранённые `(x,y,tile_id)` всех 201 активных
записей построек в трёх DE-примерах совпали с этой формулой. Дополнительно
проверена обратимость всех 320 800 индексов и отклонение координат вне ромба.
Граница хранения не равна границе игровой области: последнюю ещё нужно
проверить на крайних клетках карт разных размеров.

Обнаружено противоречие в источнике: начало `docs/grid-analysis/native-grids.md`
говорит о `y*800+x`, но текущий C# API использует упакованные индексы.
Для нашего файла следуем коду и проверке по сохранённым координатам.

### 2. Постройки: подтверждена структура и ссылки

Источник: `ReverseEngineering/structs/GameBuildingManager.h`, класс GameBuilding;
также `src/SHCDESE.BepInEx/Interop/GameBuilding.cs`.

В секции 4013 ровно 4000 записей по 812 байт (`0x32C`). Проверенные поля:

| Относительное смещение | Тип | Смысл из SE |
|---|---|---|
| 0xD0 | uint16 | состояние объекта |
| 0xD2 | uint16 | тип постройки |
| 0xD6 | uint16 | игрок-владелец |
| 0xD8 | uint32 | глобальный ID |
| 0xEE / 0xF0 | uint16 / uint16 | координаты начала постройки |
| 0xF4 | uint32 | упакованный ID начальной клетки |
| 0xF8 | uint32 | поле размера занимаемой области; смысл ещё требует проверки |

Состояния 0 и 3 исключаются из списка активных по правилу SE
(`AliveState.cs`, `IsAliveForSemaExport`). В наших записях построек активное состояние 2.

| Карта | Активные записи | Совпали координаты | Различные ID в слое 3012 |
|---|---:|---:|---:|
| Einstein 3v3 | 73 | 73 | 73 |
| Einstein 2v2 v2.0 | 72 | 72 | 72 |
| Fenrir 6 watchers | 56 | 56 | 56 |

Каждая активная запись имеет ссылки из 3012, а ссылок на отсутствующие/неактивные
записи нет. Это связывает слой 3012 с индексами слотов 4013, а не с GlobalId.
Типы взяты из `ReverseEngineering/structs/Structs16.h`: 41 — KeepTwo,
10 — GoodsYard, 71–73 — части двери замка. В каждой из трёх карт найдены восемь
KeepTwo с владельцами 1–8. Клетки каждого такого замка ссылаются на его слот
49 раз, что согласуется с площадью 7×7.
Владение замком само по себе не определяет, игрок это или наблюдатель.

### 3. Флаги поверхности и логики

Источники: `Interop/Enums/TileType.cs`, `Interop/Enums/TileProperty.cs`,
`Interop/GameTileManagerView.cs` в `src/SHCDESE.BepInEx`.

- Секция 3037 соответствует кандидату Logic2: 320 800 байт; это битовые флаги,
  а не просто нумерация текстур. Примеры: `0x10` — OasisGrass, `0x80` — ThickFoliage.
- Секция 3003 соответствует кандидату Logic: 320 800 uint32. Примеры:
  `0x20000` — камень, `0x80000` — железо, `0x1000` — растительность,
  `0x400` — постройка, `0x100000` — река, `0x80000000` — смола.
- Обе маски используются для новой схемы карты `terrain.png` и статистики.
  Совпадение размеров и связная визуальная картина поддерживают эти соответствия;
  контролируемой правкой каждой категории в игре они пока не проверены.

Для Einstein 3v3 получено 144 клетки с флагом камня и 72 с флагом железа.
Это число клеток, не число месторождений. Цвета изображения выбраны нами,
игровые спрайты в этой визуализации не используются.

### 4. Растительность и юниты: пока только кандидаты

- GameVegetation: 156 байт (`0x9C`), кандидат секция 1014.
  Состояние 0x50, тип 0x52, GlobalId 0x58, x/y 0x6E/0x70, tileId 0x74.
- GameUnit: 1168 байт (`0x490`), кандидат секция 3015.
  Состояние 0x88, тип 0x8A, GlobalId 0x94, x/y 0xC0/0xC2, tileId 0xD0.

Источники: `ReverseEngineering/structs/GameVegetation.h`, `GameUnitManager.h`
и соответствующие C# interop-структуры.
Размеры секций кратны размерам записей, но в этих DE-примерах активных записей
по runtime-фильтру не найдено. Это НЕ подтверждение правильности всех полей.
В Einstein слой 3010 содержит ссылки 1–8 при отсутствии активных записей по
этому фильтру: возможно, данные стартового состояния интерпретируются иначе.
Пока это открытый вопрос, автоматически исправлять такие ссылки нельзя.

Ещё одно различие: runtime GameVegetationManager.h описывает массив на 5000
объектов, а наша секция содержит 4000. Нельзя переносить размер менеджера в файл.

## Что меняется в архитектуре редактора

### Перенос участков — это перенос объектов со сменой ID

`GameTileManagerAPI.cs:1349` и далее реализует экспорт/импорт SEMA;
`API/Components/MapEditor/SEMAData.cs` задаёт формат версии 2 (MessagePack).
Он хранит слои, объекты, локальные координаты, владельцев и связи.
SE при вставке **создаёт новые объекты функциями игры**, строит таблицу старых/новых
ID и восстанавливает связи. Старые ID из слоёв Organism/Structure/TileUnitId/Fly
напрямую не восстанавливаются. После операции вызывается обновление графики.

Следствие для автономного редактора: не копировать прямоугольник байтов со
старыми ID. Нужны модель объектов, выделение новых слотов, обновление ссылок и
выяснение правил пересчёта производных слоёв. SEMA — полезный образец устройства
буфера обмена и возможный будущий формат обмена с SE; поддержка SEMA ещё не реализована.

### Зеркальное отражение

`ImMenu/MapEditor/MirrorTool.cs:64` переводит координаты в область текущего размера,
отражает их и вызывает действие редактора игры. Формула положения доступна, но
поворот ориентации построек и перестройка ссылок остаются задачей нашего редактора.
Слепо переносить callbacks SE во внешний процесс нельзя.

### Карта может иметь дополнительный ZIP-хвост

`API/Components/Archive/MapArchive.cs` и `docs/guides/archive-system.md` описывают
ZIP, добавляемый в конец `.map/.sav` со скриптами и metadata.
Наш парсер уже сохранял все байты после секций. Добавлена проверка: синтетический
SE-подобный ZIP остаётся побайтно тем же и читается после изменения длины сжатой
секции. Это проверка сохранности хвоста, не полноценный тест запуска SE-карты.

### Какие runtime-данные нельзя сразу считать форматом файла

В GameTileManagerView есть GFX, AlphaGFX, PillarGFX, WallGFX, pathfinding и другие
слои. Их смещения — от адреса TileManager в памяти; они **не являются смещениями
в .map**. Список секций файла нужно сопоставлять отдельно. Часть слоёв динамическая.
Документация самого SE предупреждает об экспериментальности массового редактора.

## Дополнительная находка в нашем парсере

В `2v2 Einstein SquaD v2.0.map` внешний блок миникарты содержит 165 дополнительных
байт после корректного DCL-потока, в том числе текст о правилах карты. Сжатая
часть проходит CRC32. Парсер теперь разделяет поток и дополнительные байты,
сохраняя обе части без изменений. Это обнаружено нами по файлу, не взято из SE.

Все пять исходных examples теперь читаются и побайтно пересобираются. В двух
Einstein блок 1190 остаётся непрочитанным и сохраняется как есть. Aw-Lub и Sword
имеют старую версию 170: контейнер читается, новая семантика DE к ним не применяется.
