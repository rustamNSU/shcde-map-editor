# Анализ всех 29 референсов, 19 сентября 2026

## Вывод

Набора достаточно для существенного продвижения: подтверждены основные коды
местности, геометрия хранения, три типа деревьев, лорд, состав стартового комплекса
и часть ссылок игроков. Для заявления о полном формате и надёжной записи любых
карт набора недостаточно. 130 из 175 секций не меняются во всём наборе — отсутствие
изменений не означает, что эти секции не нужны или уже понятны.

Исходные игровые карты не изменялись. Есть проверенные копии и SHA-256 каждого файла.
Все 29 контейнеров: версия 236, 175 секций; непрочитанных секций нет. Сжатые блоки
проверены по длинам и CRC32; сборка без изменений выполнена в памяти и совпала
побайтно для каждой карты. Отредактированные карты не создавались.

Данные исследования: `output/references-2026-09-19/`:

- `maps/`: точные копии всех 29 референсов.
- `provenance.json`, `source_integrity.json`: происхождение, хеши и сохранность исходников.
- `survey/`: пофайловые наблюдения, каталоги всех секций, гистограммы, записи объектов, миникарты.
- `pairs/`, `pair_index.json`: 28 сравнений соседних по времени сохранений, включая неизвестные секции.
- `findings.json`: проверенные связи, геометрия, корреляции слоёв и покрытие секций.
- `research_sources.json`: 21 использованный исходный файл из трёх проектов с хешами и commit.
- `previews.png`: контактный лист всех сохранённых миникарт.

## Метод и ограничения причинных выводов

Пользователь уточнил: часть вариантов создана заново, в части предыдущий объект
удалён и заменён. Поэтому время файлов задаёт только порядок наблюдений, а не
доказанную родословную. Перечень изменённых секций не выдаётся за точный набор
байтов, который должна менять конкретная кисть.

Мы сопоставляем: (1) содержимое внутри каждой карты, (2) изменения между файлами,
(3) независимые связи «координаты — tile ID — слой ссылок — запись объекта»,
(4) структуры и числовые ID из имеющихся исследований. Присутствуют точные
проверки полей и отдельно гипотезы. Визуально просмотрен контактный лист всех карт.

### Основные слои

| Секция | Элемент | Подтверждённое/наблюдаемое назначение |
|---|---|---|
| 3003 | uint32 | Логические флаги местности и объектов |
| 3037 | uint8 | Флаги поверхности/уровня плато |
| 3005 | uint8 | Текущая высота |
| 3045 | uint8 | Отдельная базовая высота; не обязана совпадать с 3005 |
| 3004 | uint16 | Слот дерева в секции 1014 |
| 3012 | uint16 | Слот постройки в секции 4013 |
| 3010 | uint16 | Слот юнита в секции 3015 |
| 3049 | uint8 | Тип построек в клетках; подтверждался ранее на Einstein |
| 3006 / 3007 / 3009 / 3021 / 3030 / 3036 | различные | Реагируют на редактирование; полные правила пересчёта не установлены |

Биты 3003 складываются: камень = земля 0x8000 + 0x20000; железо = земля + 0x80000;
непроходимые скалы = земля + 0x80; болото = земля + 0x20000000; смола = болото + 0x80000000.
Пара march → oil особенно сильная: на ровно тех же 2589 клетках добавился только
бит 31 в логике, а поверхность и оба слоя высот побайтно одинаковы. Но секции
3009 и 3036 тоже изменились: известный бит не является полной инструкцией записи.

### Следы истории правок

В river базовая высота 3045 побайтно совпадает с beach: в ней остался участок
из 581 нулевой клетки. Текущая высота river уже равна 0 на 1809 клетках.
Поэтому нельзя вывести правило «для любой реки установи обе высоты в ноль».
Аналогично не следует приписывать каждой кисти все различия между соседними файлами.

## Деревья: исправлена прежняя гипотеза

Секция 1014 — 4000 слотов по 156 байт. В референсах слот 1 имеет состояние 2;
слой 3004 указывает точно на этот слот; сохранённый tile ID совпадает с (x,y).

| Поле | Файловое смещение | Ранее взятое из SE runtime |
|---|---:|---:|
| state | 0x44 | 0x50 |
| type | 0x46 | 0x52 |
| global ID | 0x4C | 0x58 |
| world X/Y | 0x5C / 0x5E | 0x68 / 0x6A |
| tile X/Y | 0x62 / 0x64 | 0x6E / 0x70 |
| tile ID | 0x68 | 0x74 |

Это не команда сдвинуть ВСЮ структуру на -12: графический префикс отличается
отдельно. Названия hp/resource/growth дальше по записи пока основаны на сходстве
со структурой SE, а не на опытах изменения здоровья/роста.

В этих пустынных референсах type 1 = олива, 2 = пальма, 3 = кокосовая пальма.
SE называет те же числа Chestnut/Oak/Pine: его названия нельзя использовать как
универсальные подписи для всех ландшафтов. Сами числовые ID совпадают.

Логика клетки дерева — 0xB000. Зона TreeProximity включает для пальмы/оливы
13 клеток (ромб радиуса 2), для кокосовой пальмы — 5 (ромб радиуса 1).
Для конкретного дерева type/growth могут влиять на радиус: универсальность по
всем стадиям роста ещё не проверена. Эта зона не должна копироваться независимо от дерева.

## Юниты: найден лорд и зарезервированный слот

Секция 3015 содержит 10000 слотов по 1168 байт. Проверенные на референсах поля:
state 0x8C, type 0x8E, global ID 0x98, owner 0x80, controller byte 0x96,
tile X/Y 0xC4/0xC6, tile ID 0xD4. Это на 4 байта позже соответствующих семантических
полей SE runtime. Правило не применяется автоматически ко всем полям.

У красного замка один лорд type 55 в slot 1 на (400,402), у зелёного — на (425,394).
Владелец и controller равны соответственно 1 и 8. Слой 3010 указывает на slot 1
в точной текущей клетке лорда.

Слот 0 тоже содержит похожую запись того же global ID, но с другой позицией.
Он не имеет собственной ссылки и не должен считаться вторым юнитом. Точное
назначение этого служебного слота ещё не установлено.

Независимая проверка на прежних картах после исправления: в обеих Einstein
прочитаны по 8 юнитов, у всех совпали координаты и ссылки. Прежнее предположение
о «ссылках без юнитов» было ошибкой смещений и теперь снято. Произвольные типы
юнитов, здоровье, направления, группы/маршруты этим набором ещё не проверены.

| 1 | 41 | KeepTwo | 0,0 | 7 | 49 |
| 2 | 71 | KeepDoorLeft | 2,7 | 1 | 1 |
| 3 | 73 | KeepDoor | 3,7 | 1 | 1 |
| 4 | 72 | KeepDoorRight | 4,7 | 1 | 1 |
| 5 | 55 | Campground | 0,8 | 7 | 49 |
| 6 | 10 | GoodsYard | 7,2 | 2 | 4 |

| 8 | 10 | GoodsYard | 7,5 | 2 | 4 |
| 9 | 10 | GoodsYard | 10,5 | 2 | 4 |

Итого: пять записей комплекса замка (включая площадку Campground) и четыре
записи складских секций. Они занимают 117 клеток ссылок. Это подтверждает
уточнение пользователя и модель склада из Eco Simulator. Объединённой десятой
«записи склада» в этих образцах нет.

Для всех 18 записей world X/Y = tile X/Y × 8, поле 0xF8 равно стороне footprint,
количество ссылок равно квадрату стороны. Рабочий вход — отдельная пара 0xFE/0x100,
не противоположный угол здания, как и отмечено в Stats. У складов записана высота 18,
хотя исходная земля 8: ещё один довод не сводить размещение к записи одного ID.

Группировка пока подтверждена геометрией/владельцем и ссылками игрока. Специальное
универсальное поле parent/group для всех составных зданий не найдено.
В этих двух опытах менялись и владелец, и расположение, и global ID, поэтому
полную маску «только смена владельца» из них получить нельзя.

## Таблица игроков и связи

Секция 2022 = 9 × 0x583C байт, включая нулевой слот. Это согласуется со stride
из Rust Stats и SE. В референсах изменяется запись соответствующего игрока 1/8.

Поля: +0x94 → слот главного замка 1; +0xBC → первый склад slot 6;
+0x1D4 → Campground slot 5. Следующие три uint32 содержат координаты точки и tile ID.
Их координаты также проверены формулой сетки. +0x74 = 10 согласуется с жильём замка.

Осторожно с именами справочников: r_KeepDoorId / KEEP_DOOR_ID в этих файлах
указывает на Campground (type 55), а не на центральную дверь type 73.
Координаты при keep ID указывают на точку входа/двери, а не на начало footprint.
У первого склада X/Y в данных идут как (404,400), хотя подписи SE для полей
0xC0/0xC4 переставлены. В нашем отчёте сохраняются наблюдаемые значения.

Полную сериализацию всех player-полей, стартовых ресурсов и связей AI набор не покрывает.

## Дыры/ямы — это объекты

В `ref_08_holes_400` девять активных записей type 104 (`STRUCT_POND` в справочниках),
владелец 0. Шесть footprint 6×6 и три 9×9 дают 459 клеток, все согласованы со слоем
3012 и логикой 0x8400 (земля + постройка). Высота этих клеток не меняется.
Следовательно, инструмент с визуальным видом ям нельзя реализовать только кистью высоты.
Точное соответствие варианта спрайта и размера требует отдельной проверки.

## Геометрия игрового поля

Хранилище всегда 320 800 элементов: 800 строк длиной 2,4,...,800,800,...,4,2.
Для внутренних клеток без битов RealityEdge/MapBorder в этом наборе работает
ромб стороны `S−4`, центрированный в хранилище; число клеток `(S−4)*(S−2)/2`.
Побайтная маска по этой формуле совпала на ВСЕХ 29 картах размеров 160/200/400/500.
Это описание маски внутренних клеток, не полный алгоритм всех пограничных слоёв.

## Описание карты и служебные изменения

Пара hill → hill_map_description сохраняет все игровые tile-слои, но добавляет
`abcdefgh & 1234567890` после DCL-потока миникарты. Следом записан uint32 21 —
число байт текста. Старый 1000-байтовый блок Description остаётся нулевым.
Кодировка ASCII здесь однозначна; кириллица/Unicode этим опытом не проверены.

В распакованной миникарте изменились только байты 424..426 неиспользуемой части
палитры. Индексы пикселей и итоговое RGB-изображение идентичны. Поэтому сравнивать
сырой preview и делать вывод «картинка изменилась» без рендеринга неправильно.

Чистое пересохранение 500 меняет 10 секций: 1017, 1023, 1024, 1040, 1046, 1052,
1091, 1096, 1126, 3934. В том числе 3934 изменяется на 7193 байта. Их назначение
не объявлено полностью известным; их нельзя автоматически выкидывать или занулять.

В ref_02 обе таблицы построек и юнитов пустые до и после. Изменились, среди прочего,
1016, 2016, 2025 и 184 клетки 3036. По этим двум сохранениям нельзя восстановить
состояние удалённого объекта: самого снимка «объект ещё стоит» нет.

## Что уже можно делать и чего не хватает

Можно продолжать автономный просмотрщик, инспектор клеток/объектов, чтение
составных стартовых комплексов, точное сравнение карт и подготовку модели редактора.
Достаточно информации, чтобы не просить повторить всю эту пачку.

Ещё не доказано: безопасная запись кистей с производными слоями/проходимостью;
выделение и освобождение слотов объектов; обновление всех межсекционных ссылок;
произвольные юниты и обычные здания; расширение/удаление склада; другие варианты
и ориентации замка; условия новых/старых версий; события, ресурсы, AI и игровые настройки.
Полная работоспособность заново созданной карты требует позднее загрузки в игре.

Самый полезный следующий набор, когда перейдём к записи (сейчас есть работа без него):

1. Пустая 400 и её чистое пересохранение.
2. Из одной основы: один лучник P1; такой же лучник P8 на том же месте; два лучника P1;
   из последнего удалить одного и сохранить. Это проверит тип/владельца и жизнь слотов.
3. Один обычный домик и сохранение после его удаления.
4. Один отдельный склад; тот же склад после одного расширения; после удаления
   добавленного элемента доступным инструментом. Нужны все состояния цепочки.
5. Известная карта с кириллицей в описании — для кодировки (не блокирует работу с ASCII).

Это целевые пробелы, а не повторный запрос всего первого набора.

## Воспроизведение

```powershell
# Новый каталог назначения; команда сохраняет копии, не изменяя исходные .map.
.\.venv\Scripts\python.exe -m research.analyze_references.py 'папка с ref_*.map' output\new-reference-run

# Проверки над текущим сохранённым набором:
.\.venv\Scripts\python.exe -m research.reference_findings.py
.\.venv\Scripts\python.exe -m unittest -v
```
